# 架构设计与取舍

本文记录 RepoMind 内部的构件划分、数据模型，以及开发过程中几个关键选择背后的理由。

## 1. 构件划分

系统采用分层构件化结构，一个目录对应一个构件，对外只暴露工厂函数或装配函数：

| 构件 | 职责 | 对外依赖的抽象 |
| --- | --- | --- |
| `core` | 聊天模型、嵌入模型的创建，提示词管理 | `BaseChatModel`、`Embeddings` |
| `indexing` | 仓库加载、代码分块、向量库读写 | `Embeddings`、`Document` |
| `retrieval` | 检索器装配、RAG 问答链、会话状态 | `BaseChatModel`、`BaseRetriever` |
| `agent` | 仓库工具定义、Agent 执行器装配 | `BaseChatModel`、`BaseTool` |
| 接入层（`cli` / `app`） | 解析用户输入，调用具体构件 | 各构件的装配函数 |

依赖方向只能从上往下，`indexing` 不会 import `retrieval`，`core` 不感知任何上层。这样每个构件都能脱离整体单独测试，测试目录里的用例就是按这个边界组织的。

## 2. 核心数据模型

系统内部流转的核心数据是 LangChain 的 `Document`，各构件通过 metadata 传递结构化信息：

```python
Document(
    page_content="...",          # 加载阶段是整个文件，分块后是单个代码块
    metadata={
        "repo_name": "demo-project",
        "source": "src/bank.py", # 相对仓库根的路径
        "language": "python",
        "start_line": 4,         # 分块阶段补充
        "end_line": 12,
        "symbol": "BankAccount", # 块内首个符号定义
        "chunk_index": 1,
    },
)
```

选择把行号和符号放进 metadata 而不是拼进正文，是因为检索阶段可以直接用 metadata 做过滤（`filter={"repo_name": ...}`），生成阶段再由 `format_docs` 统一渲染成提示词需要的样子，两件事互不干扰。

## 3. 关键设计取舍

### 3.1 为什么同时保留 RAG 链和 Agent

RAG 链是固定管线：检索 → 拼接 → 生成，路径确定、延迟低、行为可预测，适合"某个功能在哪实现"这类明确问题。

Agent 是动态管线：是否调用工具、调用哪个、调用几次，由模型根据中间结果决定，适合"帮我梳理一下这个模块的结构"这类需要先探索再回答的问题。代价是延迟更高，且强依赖模型的工具调用能力。

两者共享同一套模型工厂和提示词规范，但不强行合并成一条链，避免把确定性行为变成概率性行为。

### 3.2 为什么选 Chroma 做向量库

- 纯嵌入式持久化，一个目录就是一个库，不需要单独起数据库进程，符合"本地运行、开箱即用"的目标；
- LangChain 集成成熟，支持 metadata filter 和 MMR；
- 数据量在单个仓库（几万到几十万块）规模下完全够用。

向量库的访问被收敛在 `indexing/vectorstore.py` 一个文件里，将来要换成 Milvus、Qdrant 等独立服务，只需要替换这一个构件。

### 3.3 在线与离线如何选择

| 维度 | 在线模式 | 离线模式 |
| --- | --- | --- |
| 代码隐私 | 代码片段会发送到 API | 全部留在本机 |
| 模型质量 | 商用大模型，推理与工具调用更强 | 取决于本地硬件，7B 模型日常问答够用 |
| 网络要求 | 需要外网 | 完全断网可用 |
| 资源占用 | 几乎不占本地算力 | 需要内存/显存承载模型 |

工厂模式让这个选择被推迟到运行时，而不是写死在代码里。

### 3.4 历史对话的处理方式

没有使用带状态的检索链，而是让链保持无状态，由 `ChatSession` 在外部维护消息列表。这样链本身是可重入的纯函数式管线，Web 多会话和 CLI 单会话可以复用同一条链，会话状态的存储方式（内存、数据库、Redis）也可以独立演进。

## 4. 可靠性设计

- **幻觉抑制**：提示词约束 + 来源引用 + "依据不足直接说明"的规则，答案中的每个结论都能回溯到具体代码块；
- **输入防护**：工具层路径穿越校验、正则编译捕获、subprocess 超时；
- **索引幂等**：重建索引前先删除同名 collection，重复执行不会产生重复数据；
- **测试隔离**：每个测试使用独立临时目录，测试间不共享向量库状态。

## 5. 已知局限

- 当前索引是全量重建，大仓库每次更新耗时较长，增量索引在规划中；
- 符号提取基于正则，遇到嵌套很深的宏或注解时可能漏判，静态分析方案更可靠但语言相关成本高；
- 离线嵌入模型的检索质量明显弱于商用嵌入模型，对检索精度敏感时建议在线/离线混合部署（嵌入在线、生成离线）。
